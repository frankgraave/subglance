Why section cards with a sticky index, not tabs or sub-pages. Every section here is short — a handful of fields each. Tabs would hide six cheap things behind six clicks, and sub-pages would add routes for no gain. One scrolling column keeps the whole configuration of the instance readable in a single pass, which is what you want when you are diagnosing your own server. The left rail is an index that scrolls you there and marks where you are; it is navigation, not state, so nothing is ever hidden behind it. Deep-linking still works: each card has an id, so /settings#tokens is a real address.

How much user management does a one-operator tool need? Very little — and this section is sized to that answer. The realistic second user is not a colleague with a job title, it is "someone who should be able to look at the board without being able to break it". So: two roles, flat, no groups, no per-monitor permissions, no ownership transfer, no organisation. Two roles are also the most you can add without needing a permissions matrix screen, and a permissions matrix screen is how a 12 MB binary turns into a product nobody wanted.

There is no invite flow either. Invites need email delivery, token expiry, and a public accept route — three moving parts SubGlance does not have. Add user creates the account with a password the admin sets and hands over out of band, which is what actually happens on a self-hosted box. GET/POST /api/v1/users, DELETE /api/v1/users/{id}.
Question for Frank — is even two roles too many? A viewer role has to be enforced on every write endpoint, and every new endpoint is a chance to forget. The cheaper version is: all users are admins, and read-only access is a public status page instead. Is "viewer" a real need you have had, or a need we are guessing at?

Copy-once is modelled, not just labelled. The secret lives in its own transient panel that only creation can produce and only an explicit dismissal removes — it does not fade out, and it does not survive a reload. Afterwards the token is identified by name and a four-character prefix, which is enough to answer "which one is this?" in a log line and not enough to be worth stealing. Revoke is outlined destructive on every row: it is a routine action, but it is irreversible, so it gets the colour and not the fill. GET/POST /api/v1/tokens, DELETE /api/v1/tokens/{id}.

These are per-browser preferences today. They live in localStorage, which means they follow the machine and not the person: sign in from a second laptop and you get defaults again. The chip in the card header says this browser so nobody has to discover that by surprise. It is the right trade-off for now — storing them server-side means a users table column, a migration, and a settings endpoint that does not exist yet — but it is a trade-off, not an accident.

Note that reduce motion is not merely cosmetic: the design rules require ambient animation to be switchable off, and prefers-reduced-motion is honoured whether or not the switch is touched. The switch exists for people whose system setting does not reflect what they want in this one app.
Question for Frank — should appearance preferences follow the account instead of the browser? Server-side means one round-trip before first paint (or a flash of the wrong theme), a schema change, and a settings endpoint. Browser-side means a second machine looks wrong. My instinct is: keep theme per-browser forever — it genuinely is a property of the screen you are looking at — but move layout and cards per row to the account, since those are about how you like to read, not about the display. Split them, or keep them together for consistency?

This section is the answer to a real bug, so it leads with numbers. Retention is currently hardcoded and the rollup table is never pruned — the practical effect is a SQLite file that only grows, discovered months later when a small VPS runs out of disk. A warning banner would not fix that; a banner you cannot act on is just anxiety. What fixes it is showing the operator the three tables, their real sizes, and the growth rate, with the knob right next to the number it controls. The grows unbounded chip in the header is deliberately a chip and not a red card: it states the current condition without pretending the instance is broken.

Note that row counts and sizes are per-table, not a single total — a total tells you that you have a problem, per-table tells you which retention setting to change.
Question for Frank — what should the shipped defaults be? My proposal above is 30 days of raw heartbeats, 2 years of hourly rollups, incidents forever — on the theory that raw data is only interesting while you are debugging this week, rollups are what draw the year-long uptime graph, and incidents are the history you actually re-read. That puts a busy instance somewhere around 200–400 MB in steady state. Too generous for a Raspberry Pi, too stingy for someone who wants raw latency for a quarter?

Everything here is read-only and copyable in one click. The reason this section exists is that self-hosters debug their own instance and then paste the result into an issue. "Copy diagnostics" puts version, build hash, runtime, uptime, database size and scheduler stats on the clipboard as plain text — no secrets, no database path contents, nothing that needs redacting before it goes in a public bug report.

Worker pool saturation is the number worth designing for. A monitor that silently falls behind its own schedule is the failure mode nobody notices, because the dashboard still looks green — stale checks just stop updating. Showing busy-vs-total plus queue depth makes it visible before it becomes "why did it not alert me". Queue depth at zero renders dimmed, per the numbers rule: a zero here is the good case and should not shout.

Danger zone

Reset this instance
Deletes every monitor, heartbeat, incident, notification channel and API token, and returns SubGlance to the first-run setup screen. Your user account and password are kept. This cannot be undone and there is no backup unless you made one.
Outlined, gated, and last. The destructive action is a border and a word, never a filled block — filled red at rest stops being read after the third visit. The typed confirmation is the real guard: it is the only interaction on this page that cannot be performed by a mis-aimed click, which is exactly the property you want on an action with no undo. The button stays disabled until the string matches exactly, including case.

Deliberately absent: "delete my account". On a single-operator self-hosted instance, deleting the only admin leaves a running server nobody can sign in to. If you want the instance gone, you stop the binary and delete the file — and the Instance section above tells you exactly which file that is.
What is deliberately not on this page. There is no billing, no plan, and no team or organisation management. SubGlance is self-hosted software that the reader is already running on their own server; a settings page that showed any of those would be advertising a relationship that does not exist. "Organisation" in particular is tempting as a container for users, but it would be an empty box with exactly one item in it forever — the Users section above is the whole of it, flat and honest.
