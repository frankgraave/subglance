Why this page exists at all. The Dashboard is for watching: is everything healthy right now, and if not, which one. It shows live state — heartbeat, latency, 24h uptime — and it is designed to be left open on a second screen. This page is for managing: what is configured, how it is configured, and changing it. It deliberately shows the columns the dashboard refuses to show — type, interval, timeout, retries, attached notification channels, tags, created date, paused — and deliberately drops the ones the dashboard owns: no heartbeat bar, no latency sparkline, no uptime percentage. If you can answer it by looking, it belongs on the Dashboard. If you answer it by editing, it belongs here. The one shared signal is the status LED, because you need to know what you are about to pause.

Why the row is shaped like this. Name and target take the elastic column and truncate; everything else is a fixed-width column so you can read straight down "Every" or "Channels" and spot the monitor checked once an hour or the one with no channel attached. That is the job: finding the misconfiguration, not the outage. Numbers are mono and tabular and right-aligned, and a monitor with no channels renders none in the dim zero ink rather than an empty cell — the emptiness is the finding. Row actions are inline and identical on every row: no control that only works in one view, and no hover-only "⋯" menu that hides destructive-adjacent actions behind a pointer.
Q1 for Frank — does bulk edit earn its complexity? Bulk selection costs a checkbox on every row, a select-all, a mode switch in the toolbar and a whole second set of confirm paths. A self-hosted SubGlance instance realistically has 5–40 monitors, and the honest daily need is "pause these four while we deploy" — which is one action, not four. The proposal keeps it because pause/resume during a maintenance window is the single strongest case and doing it one row at a time is genuinely annoying, and because "attach channel to all of these" is the second-most common setup chore. But bulk delete may be complexity we are buying for nobody: deleting seven monitors at once is rare and unrecoverable. Option: ship bulk pause/resume/attach, leave delete as a per-monitor action only.
Drawer, not page. Argument for a drawer: adding a monitor is almost always done from the inventory and checked against the inventory — you want to see that the name is not already taken and that the new interval matches its neighbours. A full page navigation throws that context away and adds a back-button round trip to a 60-second task. Argument against: the drawer is a third surface, the advanced section can grow taller than the viewport, and HTTP headers/body want real width. Compromise in this proposal: the drawer is the default, it is modal (it owns the screen while open, so the two-surface budget is spent on it rather than alongside the list), and the URL /monitors/new resolves to the same form rendered full-page for deep links and for the empty state. Click "Add monitor" above to open it.
60 seconds, concretely. Paste a URL and everything else is already answered: type inferred from the scheme (https:// → HTTP, host:port → TCP), name inferred from the host, interval 60s, timeout 10s, retries 3, expected status 2xx, follow redirects on. Advanced options are collapsed, not absent. Test check calls POST /monitors/preview and shows the real response before anything is saved — so the first thing a new user sees is proof the thing works, not a row that goes red because they typo'd the path. Save is one click after that.

The empty state is the onboarding. This is the literal first screen after setup, so it does the loud version: the headline states the fact, one sentence explains what the product does in the user's terms, and the primary action is a URL field that is already focusable — typing into it opens the same drawer with the value carried over. No illustration, no empty-box icon, no exclamation mark. The import line is deliberately quiet: it matters enormously to the people migrating and not at all to everyone else.
Q2 for Frank — is a separate Monitors page justified, or is it a mode of the Dashboard? The dashboard already has four layouts (Rows, Cards, Compact, Status wall). A fifth called "Manage" is a defensible alternative: one list, one search, one set of filters, and a toggle that swaps live columns for settings columns. Against it: the two views want different sort orders, different default filters (dashboard hides paused, this page must show them), and a settings view inside a screen people leave open on a wall display invites accidental edits. For it: one less nav item, and no "which page was that on" for the user. The proposal assumes separate. It is worth ten minutes of argument.
Q3 for Frank — does "Check now" belong on this page, on the Dashboard, or both? POST /monitors/{id}/check is a watching action ("is it back yet?") living on a managing page ("did my config change take?"). Both readings are real, which usually means it belongs in both places — but "no control that only works in one view" cuts the other way too: if it is here it must behave identically on the dashboard, including what it does to the heartbeat bar. Related: should "Check now" on a paused monitor be allowed? This proposal allows it (you want to verify before resuming) and disables it only for push monitors, where SubGlance does not do the calling.
